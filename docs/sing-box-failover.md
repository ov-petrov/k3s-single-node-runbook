## Путь сетевого запроса

```text
Приложение → системная маршрутизация → singtun0 → правила sing-box
  1. TCP/UDP, порт назначения 53 → hijack-dns → DNS upstream 8.8.8.8
  2. IP назначения в direct-списке → прямое соединение
  3. Остальной трафик → proxy-out → VLESS / gRPC / Reality → интернет
```

Рабочий TUN имеет адрес `172.31.255.1/30`, MTU `9000`, `stack: system`,
`auto_route: true`, `strict_route: true`. `route.final: proxy-out` задаёт
маршрут по умолчанию. `route.auto_detect_interface: true` привязывает исходящие
соединения sing-box к основному интерфейсу, предотвращая возврат в TUN.
Direct-правило содержит локальные и служебные сети, административные адреса,
адреса прокси и DNS. DNS-перехват расположен **перед** direct-правилом.

DNS использует типизированный UDP-сервер `8.8.8.8:53` без `detour`, то есть
прямое upstream-соединение. Включён кеш, стратегия — `ipv4_only`. Это стратегия
DNS, а не доказательство полного покрытия IPv6-трафика. Здесь не используются
встроенные selector/urltest: переключение выполняет внешний Python-контроллер
путём замены всего файла и перезапуска процесса.

Семантика параметров: [TUN](https://sing-box.sagernet.org/configuration/inbound/tun/),
[Route](https://sing-box.sagernet.org/configuration/route/),
[UDP DNS](https://sing-box.sagernet.org/configuration/dns/server/udp/).
В диагностике сервера зафиксирована версия `1.12.20`; текущая upstream-документация
также описывает более новые версии. Их поля нельзя автоматически переносить
в этот конфиг без проверки совместимости.

## Подготовка кандидатов

Импортёр получает базовый полный конфиг и JSON с массивом `outbounds`.
Для каждого элемента он:

1. Копирует базовый конфиг и подставляет выбранный outbound с тегом `proxy-out`.
2. Сохраняет остальные outbound базы, кроме прежних `proxy-out` и `proxy-fallback-nl`.
3. Устанавливает `route.final = proxy-out`.
4. Дополняет первый direct-список `ip_cidr` адресами **всех** серверов каталога.
5. Сохраняет отдельный JSON и запись inventory с именем `cfg-00`, `cfg-01` и т. д.

Приоритеты назначаются по порядку каталога: `100`, `99`, `98` и далее, минимум
`1`. Все импортированные записи включены. Импорт не проверяет их сетевую
доступность, не выполняет `sing-box check` и не меняет активный TUN.

Ограничения импортёра: адрес `server` механически получает суффикс `/32`, поэтому
этот путь рассчитан на IPv4-адреса, а не DNS-имена или IPv6. Если direct-правила
в базе нет, новое не создаётся. Имена зависят от порядка каталога; перестановка
или замена каталога требует согласовать прежнее состояние и результаты пула.
Импорт перезаписывает inventory и не добавляет поля настройки пула/full probe:
после генерации их нужно перенести из примера inventory.

## Что считается здоровым маршрутом

| Проверка | Реальное условие успеха |
| --- | --- |
| Telegram у контроллера | HTTP-запрос `getMe` завершился без HTTPError; JSON содержит `ok: true` |
| Telegram в pool probe | `curl` завершился с кодом 0; JSON содержит `ok: true` |
| Codex transport у контроллера | Успешное завершение `urlopen` либо HTTPError с кодом `401`, `403`, `404`, `405` |
| Codex transport в pool probe | `curl` завершился с кодом 0 и вернул числовой HTTP-код больше 0, включая `429` и `5xx` |
| Codex full | Команда из `OPENAI_CHECK_COMMAND` завершилась с кодом 0; текст ответа не проверяется |

На сервере `require_both_apis: true`: контроллер требует успеха Telegram **и**
Codex. Pool probe всегда использует логическое И и не читает этот параметр.
Контроллер поддерживает `TELEGRAM_API_BASE_URL`, а pool probe использует
жёстко заданный `https://api.telegram.org`.

Transport-проверки не генерируют LLM-ответы. HTTP `403`, принятый как здоровый,
доказывает только получение HTTP-ответа, но не работоспособность OAuth или
генерации. При full probe запускается Hermes с запросом `Reply with OK only`.
На момент среза команда в env указывает `openai-codex` и `gpt-5.4-mini`;
это отдельная настройка, которая не обязана совпадать с основной моделью Hermes.
В данном обследовании full-команда не запускалась.

## Обследование пула

`singbox_pool_probe.py` читает включённые конфиги из inventory и обходит их
последовательно. Для каждого кандидата:

1. Находит свободный локальный порт, начиная с `2080 + индекс`.
2. Создаёт временную копию конфига; заменяет все inbound одним `mixed` на
   `127.0.0.1:<порт>`, сохраняет outbound, DNS и правила маршрутизации.
3. Запускает отдельный `/usr/local/bin/sing-box run`, ждёт открытия порта до 8 секунд.
4. Проверяет Telegram и Codex через `http://127.0.0.1:<порт>`.
5. Останавливает временный процесс и переходит к следующему кандидату.
6. В конце записывает весь массив результатов в файл `--out`.

Основной TUN и его файл при этом не заменяются. Для HTTP-проверок используется
`curl --proxy`; в full-режиме дочерней команде задаются `ALL_PROXY`, `HTTP_PROXY`,
`HTTPS_PROXY`. Изоляция full-проверки зависит от того, учитывает ли команда эти
переменные: сетевого namespace или принудительной проверки пути нет.

Плановый обход использует `transport` и таймаут запросов 10 секунд. Full probe
вызывается контроллером отдельно для кандидата перед попыткой переключения.
Он может выполниться для нескольких кандидатов подряд, если предыдущие не прошли.
Скрипт пула возвращает код 0 и при **нуле здоровых кандидатов**: успешный systemd
запуск означает завершение обследования, а не наличие рабочего резерва.

## Алгоритм контроллера

```text
Загрузить inventory и state → определить имя активного кандидата
  → проверить Telegram + Codex transport
    → здоров: обновить state и закончить
    → нездоров / неизвестен: прочитать свежий здоровый пул
      → при необходимости попытаться отправить предварительное уведомление
      → перебрать разрешённых кандидатов по приоритету
        → sing-box check → изолированный full probe
        → копирование конфига → restart → ожидание 5 секунд
        → повторная Telegram + transport проверка
          → успех: сохранить state, историю, уведомить, закончить
          → неуспех: перейти к следующему кандидату
      → варианты исчерпаны: записать ошибку, закончить без rollback
```

Подробности отбора:

- Файл результатов должен существовать и иметь возраст по `mtime` не более
  `43200` секунд. Собственное время проверки каждого кандидата не учитывается.
- Берутся только `healthy: true`, включённые в inventory записи, кроме текущей.
- Сортировка: приоритет по убыванию, затем имя по возрастанию. Скорость ответа
  и свежесть последнего успеха не участвуют в сортировке.
- Кандидаты с ещё не истёкшим `cooldown_until` пропускаются.
- Нет подходящего пула — выход с кодом 1; внеплановое обновление не запускается.
- Если основной маршрут здоров, контроллер вообще не анализирует пул и не
  возвращается автоматически на более приоритетный маршрут.

В рабочей настройке применяется `copy-and-restart`: `shutil.copy2` заменяет
`/etc/sing-box/config.json`, затем выполняется `sudo -n systemctl restart sing-box-tun`.
В коде также есть `symlink-and-restart`, но на сервере выбран режим копирования.
Поле `singbox_service_name` само по себе не управляет рестартом — выполняется
строка `singbox_restart_command`.

После успеха сохраняются `active_name`, `last_known_good`, `last_switch_at` и
запись в истории, ограниченной двадцатью переключениями. После исчерпания
вариантов возвращается код 1. В `--check-only` нездоровый/неизвестный активный
конфиг даёт код 2; здоровый — код 0.

## Состояние и определение активного конфига

Сначала используется `state.active_name`. Только если оно отсутствует или пусто,
`_detect_active_name()` проверяет symlink, а затем сравнивает live outbound
`proxy-out` с кандидатами по `server`, `server_port`, `uuid`.

Это не сравнение всего конфига: изменения TLS, Reality, transport и правил
так не обнаруживаются. Даже если имя из state больше не существует в inventory,
повторного определения по live-файлу в этом запуске не происходит. При ручном
обслуживании нужно отдельно сверять фактический файл с кандидатом, затем
согласовывать state при остановленном контроллере.

На кандидата сохраняются время успеха/ошибки, число последовательных сбоев,
`cooldown_until`, последняя ошибка и признак отправки предварительного уведомления.
Успешная проверка сбрасывает ошибки, cooldown и признак уведомления. Ошибка
валидации, full probe или применения сразу выставляет cooldown на 900 секунд.
Для API-проверок cooldown выставляется при достижении порога в два сбоя.

**Порог не задерживает переключение.** После первого неуспешного active check
контроллер уже начинает поиск замены. `consecutive_failures_before_switch: 2`
фактически влияет на cooldown и предварительное уведомление, хотя название
параметра обещает другое поведение.

## Расписания, права и уведомления

| Задание | Первый запуск после загрузки | Повторение |
| --- | --- | --- |
| `singbox-failover.timer` | Через 2 минуты | `OnUnitActiveSec=5min` |
| `singbox-pool-refresh.timer` | Через 3 минуты | `OnUnitActiveSec=12h` |

Это интервальные systemd timers, не фиксированные часы календаря. На сервере
оба сервиса — `Type=oneshot`, без `User=`, то есть запускаются от root.
`HOME=/home/petrovov` и `HERMES_HOME=/home/petrovov/.hermes` задают пути, но не
меняют пользователя процесса. Full probe также запускает Hermes от root и
может создавать root-owned файлы в пользовательском хранилище.

Контроллер пишет JSON в stdout/journal и `failover.log`. При достижении порога
сбоев пытается отправить одно предварительное Telegram-уведомление, включая
основного кандидата на замену. После успешного post-switch check пытается
отправить уведомление о выполненном переключении. Здоровые циклы не уведомляют.
Признак предварительного уведомления сохраняется даже при неудачной отправке,
поэтому повторной попытки в том же эпизоде сбоя нет. Отдельного гарантированного
канала оповещения об исчерпании пула не реализовано.

## Ограничения, которые нужно учитывать при доработке

1. **Нет автоматического rollback.** Предыдущий файл не резервируется, а
   `last_known_good` не используется для восстановления. Если рестарт или
   post-switch check неуспешен, на диске может остаться последний применённый
   кандидат, а state продолжит называть старый.
2. **Порог двух сбоев не защищает от раннего переключения.** Cooldown ограничивает
   повторный выбор кандидата, но не задаёт минимальное время работы текущего.
3. **Проверки transport неодинаковы и не проверяют авторизацию.** Пул может
   считать здоровым ответ `5xx`, который контроллер отвергнет.
4. **State может устареть.** Нет обязательной сверки с live-файлом, идентичность
   кандидата определяется не полным содержимым, а результаты пула привязаны
   к имени без хеша конфига.
5. **Записи неатомарны, общей блокировки нет.** Копирование активного файла,
   запись state и результатов пула выполняются напрямую. Таймеры, ручные
   запуски и обслуживание не координируются общей блокировкой.
6. **Истёкший/пустой пул останавливает failover.** Контроллер не перепроверяет
   отвергнутых кандидатов по требованию; TTL пула совпадает с периодом его
   обновления, поэтому задержка нового обхода может создать окно просрочки.
7. **`--dry-run` имеет побочные эффекты.** Не применяет конфиг, но может запустить
   full probe, потратить LLM-токены, изменить state/log и отправить предварительное
   уведомление. `--check-only` также выполняет запросы и обновляет state/log.
8. **Probe не гарантированно завершается вовремя во всех ветках.** Если порт
   не открылся, но процесс ещё жив, чтение `proc.stderr.read()` может блокировать
   обход. Сбор stdout/stderr через PIPE без постоянного чтения тоже требует
   внимания при дальнейшем укреплении реализации.

Документация исходного серверного skill содержит рекомендации о rollback,
пороге сбоев и политике уведомлений. Здесь приоритет отдан тому, что фактически
реализовано в приложенных скриптах. Эти ограничения в данном обновлении
документации не исправлялись.

## Работа с приложенными файлами

Зависимости скриптов: Python 3.10+, PyYAML, `curl`, `/usr/local/bin/sing-box` и
systemd для применения. Для full probe нужна рабочая команда Hermes с доступом
к соответствующему auth store. Синтаксис probe-конфига соответствует снимку
sing-box 1.12.20; совместимость с другими версиями здесь не проверялась.

Примеры:

- [inventory.example.yaml](../sing-box/failover/templates/inventory.example.yaml)
- [failover.env.example](../sing-box/failover/templates/failover.env.example)
- [singbox-failover.service](../sing-box/failover/templates/singbox-failover.service)
  и [timer](../sing-box/failover/templates/singbox-failover.timer)
- [singbox-pool-refresh.service](../sing-box/failover/templates/singbox-pool-refresh.service)
  и [timer](../sing-box/failover/templates/singbox-pool-refresh.timer)

Шаблоны нужно адаптировать: заменить `<USER>`, `<MODEL>`, секреты, пути кандидатов
и проверить права каталогов. Реальные конфиги и env должны храниться вне Git,
с ограниченным доступом. Скрипты сами не загружают `.env`; штатно окружение
передаёт systemd через `EnvironmentFile`. В примерах units сохранена модель
запуска от root; установка `HOME` не понижает привилегии.

Для проверки целостности копий и просмотра CLI без работы контроллера:

```bash
cd sing-box/failover
shasum -a 256 -c SHA256SUMS
python3 scripts/singbox_failover.py --help
python3 scripts/singbox_pool_probe.py --help
python3 scripts/import_outbounds_catalog.py --help
```

Для наблюдения на сервере без ручного запуска автоматики:

```bash
sudo systemctl status sing-box-tun.service --no-pager
sudo systemctl list-timers 'singbox-*' --all --no-pager
sudo systemctl show singbox-failover.service singbox-pool-refresh.service \
  -p ExecMainStatus -p ActiveState -p SubState
sudo journalctl -u singbox-failover.service -n 30 --no-pager
sudo journalctl -u singbox-pool-refresh.service -n 30 --no-pager
```

Вывод журналов, состояние и конфиги перед публикацией нужно обезличивать:
скрипты сохраняют тексты ошибок внешних команд и HTTP-запросов, где могут
оказаться адреса и секреты. `state.active_name` и зелёный статус timer не
заменяют сверку live-конфига и результатов проверки пула.
